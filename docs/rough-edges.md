# Rough edges

Known simplifications and gaps in the current design. They are deliberately deferred so we can get a prototype running quickly, and will be cleaned up as we reach the relevant parts of the codebase. This page exists so we don't forget them.


## Deferred items

- **Public storage quota is measured late** — the `api` service never sees *File* bytes, so the [public access](public-access.md) storage cap is totalled by a periodic sweep against MinIO rather than enforced as uploads arrive, and can be overshot by up to one sweep interval's worth of traffic. There is also no cap on the number of *Files* per page, so the byte quota is the only bound on public disk. Both are tolerable because the quota sits well under MinIO's capacity and nginx caps each single upload; a per-page file count would tighten it if the slop turns out to be too loose.
- **Page eviction vs. active executions** — the `api` service may evict *Musicorpus Pages* under disk pressure, but the policy is undefined. At minimum it should not evict a page that has a running *Pipeline Execution*, and the client-visible behaviour of hitting an evicted page (a sudden `404` while polling) needs deciding.
- **Stray-write garbage in MinIO** — after a `DELETE` or a timed-out execution, a still-running *Worker* or *Model* may keep writing into a page folder that the `api` service no longer tracks, leaking disk until the next `api` startup wipe. Acceptable for now.
- **Path traversal** — `core` now validates page IDs and file paths (`musibot.core.page`), and refuses anything that could leave a page's folder, symbolic links included. What remains is making sure every call site actually uses it: the file endpoints in the `api` service, and the paths a *Worker Head* accepts back from a *Model*.
- **File-change detection in the worker head** — the *Worker Head* now compares each file's size and modification time against a snapshot taken just before the model ran, and uploads whatever differs. Two gaps remain: *deletions do not propagate*, and a file rewritten to the same size within the same clock tick would be missed. Neither matters for a *Model*, which produces new *Files* rather than removing or silently rewriting old ones, but a content hash would close both if one ever does.
- **Per-model timeout** — only the pipeline-level timeout exists today, so a hung *Model* ties up a *Worker* for the whole pipeline budget. A per-model watchdog may be worth adding.
- **No Musicorpus helpers for a *Pipeline*** — slicing a page into staff crops and concatenating staff MusicXML into a page-level file are wanted by every real *Pipeline*, and Musibot provides neither, so each *Orchestrator* writes its own. They do not belong in the *Orchestrator Head*, which knows only that a *File* is bytes; they belong in a Musicorpus library that a *Pipeline* depends on the way it depends on Pillow. Until that exists, [Writing pipelines](writing-pipelines.md) shows the slicing written out by hand.
- **A chatty *Pipeline* loses log lines rather than blocking** — an *Orchestrator Head* queues what its *Pipelines* say and publishes it from one task, bounded at a thousand messages, dropping the excess with a warning. That is the right trade for a fire-and-forget stream, but it means a *Pipeline* logging faster than the broker accepts silently narrates less than it thinks. The process's own log keeps every line, so nothing is truly lost — see [orchestrator-head](../components/orchestrator-head/README.md).
- **Nothing checks that everyone is on the same `core`** — `core` is the wire contract, but no process announces which version of it it is running and none would refuse a peer that disagreed. A *Worker Head* does announce `head_version`, its own component version, and the `api` service discards it without looking. So a *Worker* left on an older `core` after a protocol change is not rejected, not logged and not visible in `GET /pipelines`; it simply misbehaves in whatever way the change implies, on a *Worker* that may not even be on the same VM. Keeping the fleet in step is currently a deployment procedure (see [Deploying onto a VM](deploying-to-a-vm.md)) rather than anything the system verifies. The cheap fix is to put `core`'s version into the announcement and have the registry report — or refuse — a mismatch; the announcement already carries a version field that goes unused.
- **MinIO is no longer maintained** — the project stripped its administrative Console down to a bare object browser in mid-2025 and archived its repository in April 2026, so `RELEASE.2025-09-07T16-13-09Z` is the last community build and there will be no security updates. Nothing is broken by this: it is a working S3 server, `mc` does what the Console used to, and Musibot depends on ordinary S3 plus SigV4 rather than on anything MinIO-specific. But it is a dependency with no future, and replacing it is a decision this deployment will have to make. Note that the S3 constraint that shapes the storage names (see [Deployment](deployment.md)) is SigV4 and path-style addressing rather than MinIO, so a replacement inherits it.
- **A log is only seen if somebody is watching when it happens** — the `api` service forwards log lines to whoever is subscribed and drops the rest, keeping no buffer, so a browser reload loses the log of a reading that has already finished and a client that starts watching late sees only the rest. This is the intended shape (see [the HTTP API](http-api.md)) and the alternative — a ring buffer per page in the one service that holds all the state — was not worth its cost while an execution takes a second or two. Revisit if reading a finished page's log turns out to be something people want.
- **An idle watcher holds three connections** — a page screen keeps the page's log stream, its file-change stream and the *User*'s result stream open for as long as it is open, so an abandoned tab costs three connections and three subscriptions in the `api` service until the page expires. They are separate because their consumers are: a client wanting to know that a page finished should not have to read a model's warnings to find out. The trade was deliberate — it replaced a request every 1.5 seconds per open page — but it moves the cost from requests to sockets, and the one service that does not scale holds them. If that ever bites, the page-scoped pair could become one stream with typed events without changing what anything is told.
- **RabbitMQ reconnection recovery** — the `api` service connects with aio-pika's robust connection, which reconnects on its own and is expected to re-declare its consumers after a broker bounce. That recovery has not been tested against an actual RabbitMQ restart, so whether every subscription (results, discovery, logs) comes back cleanly — and whether messages published during the gap are lost — is unverified. Harden when we exercise failure modes.
